Services. The leaf directory path in =bro_dockerfiles= is the configuration ---

| Path segment | Parameter derived                                               |
|--------------+-----------------------------------------------------------------|
| =debian=       | distro                                                          |
| =<release>=    | 12 or 13 → base OS, base image tag                              |
| =<profile>=    | =confined= / =privileged= / =rootless-sysd= → engine, init, privilege |

* Stage 4: Implement the Platform Registrar -- Future None-Urgent 

Goal: Make the design in the =containerProcArchitecture= figure real.
Introduce a per-user, per-image, per-instance registrar on the Container
Platform that assigns host-side ports, so multiple users on one VM ---
and multiple instances of one image per user --- no longer collide on
the fixed 2222/2223/... port table. The same registrar also assigns each
instance its cgroup v1 bridge subnet (see "cgroup v1 subnets" below).

The registrar is a =bisos.regfps.RegFPs= subclass following the precedent
of =bisos.siteRegistrars.containerRegfps.Container_RegFPs=. Storage
lives at =/bisos/platform/registrar/dockerProc/<user>/<imageName>/instance<N>/=;
each instance directory is a =RegFPs= unit whose file-parameters
carry the assigned =sshPort= / =vncPort= / =novncPort= / =cgv1Subnet= (plus
=engine=, =profile=, =plantPath=, =createdAt= for diagnostics).

** cgroup v1 subnets --- why the registrar must assign them too

Found in Stage 6 ([[6.1]], 2026-10). On a cgroup v1 host (RHEL 8) the privileged sysd leaves run
from =docker-compose.cgv1.yml=, which gives each container its own bridge network on an *explicit*
subnet, because the host's default docker address pools can be exhausted ("all predefined address
pools have been fully subnetted"). An explicit subnet is a host-global resource, like a host port:
- Two instances with the same subnet cannot both be created: =bisos_deb13-sysd-2= started as a copy
  of =bisos_deb13-sysd= and carried its subnet.
- A subnet can overlap the host's own networks. The first choice, =10.254.x.0/24=, was moved to
  =172.16.x.0/24= after on-host verification (bro_dockerfiles commit 376e74e).

Today the subnets are hand-picked per leaf, in each =docker-compose.cgv1.yml=:
=172.16.11.0/24= (deb12-sysd), =172.16.12.0/24= (deb13-sysd), =172.16.13.0/24= (deb13-sysd-2).
The standalone =containerManage.sh create= refuses a subnet that overlaps a docker network or a
host route; that check detects a collision but does not allocate. With many users and instances
per VM, the registrar must allocate the subnet with the ports, atomically, from a pool reserved in
=bisos.banna=. The cgroup v2 compose files need no explicit subnet; =cgv1Subnet= is assigned to
every instance anyway (cheap; an instance may be created on either kind of host).

Two consumers must be wired --- =.spcs= (on the platform) and Remote User
(over ssh). The design figure already shows both.

** Storage layout (registrar file tree)

#+begin_src
/bisos/platform/registrar/dockerProc/
  <user>/                          # posix login name
    <imageName>/                   # e.g. bisos_deb13-sysd
      instance0/                   # RegFPs unit dir
        fps/
          sshPort/value            # assigned host-side ssh port
          vncPort/value
          novncPort/value
          cgv1Subnet/value         # e.g. 172.16.37.0/24 --- bridge subnet on cgroup v1
          engine/value             # docker | podman
          profile/value            # confined | privileged | rootless-sysd
          plantPath/value          # source leaf path (for round-trip)
          createdAt/value          # ISO timestamp
      instance1/
      ...
#+end_src

Port allocation pool: e.g. =sshPort= in =20000--29999=, =vncPort= in
=30000--39999=, =novncPort= in =40000--49999=, allocated by
=unitsNextNu()= against the union of already-assigned ports in that pool
(scanning all users, since ports are host-global).

Subnet allocation pool: e.g. =172.16.0.0/16= carved into =/24= blocks (256 instances per host),
the lowest =/24= not assigned in the registrar *and* not overlapping a docker network or a host
route on this host (the same check =containerManage.sh= does). Docker's own default pools are
=172.17.0.0/16= upward and =192.168.0.0/16=, so =172.16.0.0/16= does not collide with them.
The current hand-picked =172.16.11-13.0/24= lie inside it and should be adopted, not reallocated.

* Stage 7: =/shuttle/share= --- a Per-Instance Directory Shared with the Host

Goal: every systemd instance (privileged and rootless-sysd leaves; not confined) gets a directory
shared with the host, for convenient exchange of files between host and container:

: host:       /var/container/<user>/<containerName>/
: container:  /shuttle/share

On by default. Both ways (standalone =containerManage.sh= and =bisos.dockerProc=) at parity.
Replaces the earlier =/shuttle/home= idea (mount the host user's whole =$HOME=), dropped
2026-10-26 by user decision: too much exposure (=~/.ssh=, =~/.gnupg=), and it needed the confined
entrypoint reworked.

** Design (agreed 2026-10-26)

- *Profiles:* privileged (docker) and rootless-sysd (podman). Not confined.
- *Host path:* =/var/container/<user>/<containerName>/=. =<user>= is the host user running
  =create=; =<containerName>= the leaf's container name (so =bisos_deb13-sysd-2= gets its own).
  Per user because rootless podman container names are only unique per user. Same path in both
  ways.
- *=/var/container=:* created once per host by an admin, root-owned, mode 1777 (sticky, like
  =/tmp=): =sudo install -d -m 1777 /var/container=. Each =<user>/= below it is created and owned
  by that user.
- *On by default.* An option to opt out at create (name to decide in 7.1). If =/var/container= is
  missing, =create= refuses and prints the admin command above, rather than silently skipping the
  mount.
- *Lifecycle:* =create= makes =<user>/<containerName>/= if missing (=-n= shows that it would).
  =delete= leaves it, and prints its path: the data outlives the container. =status= shows the
  path. Removing the data is =rm -r= by the user; no verb for it.
- *Ownership --- no image change, no rebuild:*
  - *docker (privileged):* container UIDs are host UIDs; the container's =bystar= is UID 1000
    (=useradd= without =-u= in the confined =Dockerfile=; confirm with =id bystar=), the host
    user U may differ. =create= gives the directory POSIX ACLs, access and default, for U and for
    UID 1000: =setfacl -m u:U:rwx,u:1000:rwx,d:u:U:rwx,d:u:1000:rwx <dir>=. Files the container
    writes show as UID 1000 on the host, and U can still read, edit and delete them (and the other
    way round). Needs =setfacl= (Debian package =acl=) and ACL support on the filesystem under
    =/var= (ext4, xfs: yes). If U is 1000, the ACL is harmless.
  - *podman (rootless-sysd):* =--userns=keep-id:uid=1000,gid=1000=, so the host user appears as
    =bystar= inside and the files are simply the user's. Debian 13 (podman 5.4.2) is the primary
    target; Debian 12 (podman 4.3.1) is not.
- *Where it is declared:*
  - docker: in each privileged leaf's =docker-compose.yml= and =docker-compose.cgv1.yml=, a volume
    =/var/container/${USER}/<containerName>:/shuttle/share= --- the compose file stays the one
    source of truth. Opting out needs it removed at create: compose cannot drop a volume by
    override, so the opt-out path is a variable that defaults to the share, or a generated
    override (decide in 7.1).
  - podman: in the Quadlet =*.container= file (=Volume== and =UserNS==), which =containerManage.sh=
    already reads for name and ports; =containerManage.sh= reads these too.
  - =containerManage.sh= reads the path from the file, creates and ACLs the directory, and does
    nothing for the confined leaves.
- *bisos.dockerProc:* =instanceUp= creates the directory and sets the ACL the same way for
  docker leaves (the compose file carries the volume), and passes =-v= / =--userns= for podman.
  Same opt-out parameter. Its =cgroup v2 only= rule is unchanged.
- *Fix regardless:* =common/raw-bisos/postRawBisos.sh= runs =sudo chown -R bystar:bystar
  /shuttle/this=, which on a host where U ≠ 1000 changes the ownership of the leaf *in the git
  checkout on the host*. Remove it; =/shuttle/share= must never be chowned either.

Effort: small to medium. No image change. Compose and Quadlet edits in five leaves (deb12-sysd,
deb13-sysd, deb13-sysd-2, two rootless), directory + ACL logic in =containerManage.sh= and in
=containerProc_csu.py=, docs. VM tests: docker with U = 1000 and U ≠ 1000; rootless podman on

* Stage 8: Optional VNC Passwords

Goal: an instance can have a VNC password, opt-in. *No password stays the default* --- it is the
convenient way for local development and must not be lost. Both ways at parity.

** Assessment (2026-10-26)

Today: TigerVNC runs with =-SecurityTypes None --I-KNOW-THIS-IS-INSECURE= (=vncserver.service= in
the sysd images, =entrypoint.sh= in the confined ones); =websockify= serves noVNC on 6901 and
relays to 5901 with no authentication of its own. noVNC already prompts for a password whenever
the VNC server asks for one, so *noVNC needs no change*.

- *Mechanism (proposed):* the password lives in the container, at TigerVNC's standard
  =~bystar/.config/tigervnc/passwd= (the format =vncpasswd= writes). A small start script in the
  image, used by =vncserver.service= and by the confined entrypoint, picks the security type at
  each start: file present → =-SecurityTypes VncAuth= (with that file); absent → =None= as today.
  No password, no change in behaviour.
- *Setting and clearing:* a new =containerManage.sh= verb, e.g. =vncPassword set|clear=: =set=
  reads the password without echo, produces the file with the image's own =vncpasswd -f= (in a
  throw-away =--rm= container, so no TigerVNC is needed on the host), copies it in with
  =docker cp= / =podman cp= (works on a stopped container too), fixes its owner and mode (0600),
  and restarts the instance. =clear= removes it and restarts. Using =cp= rather than =exec= avoids
  the =podman exec= failure on Debian 12's podman 4.3.1. =status= shows "VNC auth: none |
  password".
- *Lifetime:* the file is in the container's writable layer: it survives stop/start/restart and is
  lost on =delete=, like everything else in the container. (Alternative, if preferred: a host-side
  file mounted at create. That ties it to create time and needs a place for secrets outside git.)
- *bisos.dockerProc:* =containerProc_instanceVncPassword= with =set= / =clear=.
- *Limits, to document:* classic VNC authentication uses only the first 8 characters of the
  password, and it protects the password, not the traffic: VNC and noVNC still travel unencrypted.
  For use over a network, keep using an SSH tunnel, or add TLS later (TigerVNC's VeNCrypt types
  for viewers, =websockify --cert= for noVNC) --- out of scope here.
- *Related, not in scope:* binding the published ports to =127.0.0.1= (from PriorAndSimilarArt.org)
  is what makes the passwordless default safe on a shared VM; it could become a create option of
  its own. The SSH password (=insecure=) and =root:password= in the confined =Dockerfile= are
  separate.

Effort: small to medium. One start script and the unit / entrypoint change (and a rebuild); one
verb in each way; docs. Less than Stage 7: no UID questions.

* Stage 9: Ordered, Gated Walks over the deb13 Tree --- Rebuild Images, Re-materialize Instances

Goal: after a change that needs new images (e.g. Stage 8's =vncStart.sh=), one walk from
=bro_dockerfiles/debian/13/= rebuilds the images in dependency order, and a second walk recreates
only the instances that are stale *and* whose owner has enabled that, modelled on the CBM
collective (=/bisos/platform/sys/cbm/collective/=: =cbmProc.control= gate, =cbmProc.status= log,
=branchesOrdered=, =cbm_materialize= / =reMaterialize= / =unMaterialize=). Scope (user decision
2026-10-26): *deb13 only*, *=bisos.dockerProc= only* --- the bash leaf scripts and deb12 stay as
they are. The new verbs are generic; only the deb13 branch files get the ordering.

** Why (assessment 2026-10-26)

- *Images depend on each other:* confined first; privileged and rootless-sysd are =FROM= it;
  =bisos_deb13-sysd-2= runs =bisos_deb13-sysd='s image. Today the walk order is discovery order.
- *Rebuilding an image does not update its containers:* a container keeps the image it was
  created from until it is deleted and created again; a restart is not enough.
- *Recreating destroys the container's state*: the Raw-BISOS installation, the Stage 8 VNC
  password, anything done inside. Hence the gate, with a safe default, and a read-only staleness
  check to see what would be recreated before anything is. Stage 7's =/shuttle/share= is outside
  the container and survives a recreate: the place for what should be kept.
- *One user per VM* (user clarification 2026-10-26): each user has their own VM with their own
  clone of bro_dockerfiles. Everything in a clone --- gates, logs, images, instances --- belongs to
  that one user and that one VM. Gates and logs must not be pushed: they describe one VM.

** Design

- *Prerequisite --- the numeric-suffix rule in =paramsFromPlantPath()= (see Stage 6, 6.1):* for a
  leaf =<primary>-<N>= the image is =<primary>='s, and =imageBuild= builds nothing there. Ports
  (and container name) come from the leaf's compose file (docker) or Quadlet file (podman), as the
  standalone scripts already read them, so =_PORT_TABLE= stops being a second source of truth.
  Without this, a walk would build a separate =bisos_deb13-sysd-2= image from the leftover
  =Dockerfile= and check the wrong ports.
- *Order:* =branchesOrdered = [confined, privileged, rootless-sysd]= in
  =debian/13/ftoBranchProc.spcs=; =leavesOrdered = [bisos_deb13-sysd, bisos_deb13-sysd-2]= in
  =debian/13/privileged/vnc/xfce/= (or wherever the walker reads leaf order --- check
  =bisos.fileObj=). deb12 untouched.
- *Gate and log in the leaf, as in CBM:* next to the leaf's planted file, named after it ---
  =dockerProc.control= / =dockerProc.status= in docker leaves, =podmanProc.control= /
  =podmanProc.status= in rootless-sysd leaves:
  : <leaf>/dockerProc.control   # enabled | available | disabled
  : <leaf>/dockerProc.status    # timestamped lines, appended
  States and default as in CBM: missing file = =available= (the walker skips; nothing destructive
  happens until the user enables an instance). *Never pushed:* =*Proc.control= and =*Proc.status=
  go into bro_dockerfiles' =.gitignore= (unlike bro_rawBisos, which commits its =cbmProc.*=: there
  the files describe the platform tree; here they describe one VM).
- *Gate code:* a small copy of =bisos.capability.cbmProc_seedInfo='s =controlRead= /
  =controlWrite= / =statusWrite= in =bisos.dockerProc= (parameterized by directory), not a
  cross-package change now; factoring it into a shared module is a later option.
- *New =bisos.dockerProc= commands:*
  | Cmnd                                    | Kind        | Does                                                         |
  |-----------------------------------------+-------------+--------------------------------------------------------------|
  | =containerProc_control=                 | read-only   | show this user's gate state for the instance                 |
  | =containerProc_status=                  | read-only   | show this user's status log for the instance                 |
  | =containerProc_enable= / =_disable= / =_available= | gate | set the gate                                        |
  | =containerProc_imageIsStale=            | read-only   | image older than its base image (rebuild needed)             |
  | =containerProc_instanceIsStale=         | read-only   | instance's image ID ≠ the tag's current image ID             |
  | =containerProc_materialize=             | gated       | enabled → =instanceUp= (idempotent: running is a no-op)      |
  | =containerProc_reMaterialize=           | gated       | enabled and stale → save VNC password, =instanceDelete=,     |
  |                                         |             | =instanceUp=, restore VNC password; else skip (logged)       |
  | =containerProc_unMaterialize=           | gated       | enabled → =instanceDelete=                                   |
  Every gated run appends a status line: =ran: reMaterialize ok=, =skipped: control=available=,
  =skipped: not stale=, =failed: ...=. The VNC password is the only in-container state preserved;
  a Raw-BISOS installation is not (documented; the default gate protects it).
- *The two walks (from =debian/13/=):*
  : ./ftoBranchProc.spcs -i fto_forwardToLeaves --cmndName=containerProc_imageBuild          # A, ordered
  : ./ftoBranchProc.spcs -i fto_forwardToLeaves --cmndName=containerProc_instanceIsStale     # look first
  : ./ftoBranchProc.spcs -i fto_forwardToLeaves --cmndName=containerProc_reMaterialize       # B, gated
  Phase A is not gated (building does not destroy an instance). On a VM it rebuilds that VM's
  images only --- no cross-user effects.
- *=walkExamples()=:* add the new verbs with tags (=read-only=, =control=, =destructive=), so
  every branch's examples menu shows them.
- *cgroup v2 only*, as all of =bisos.dockerProc= (since 2026-10-26).

Effort: medium. The suffix rule and compose/Quadlet reading are the base; gate + log + seven
verbs + staleness are mostly small; the ordering is two branch-file edits. VM tests on a deb13
VM.
